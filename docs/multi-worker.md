# 多 worker：現況、名詞、以及要做的話怎麼做

這份文件回答一個問題：如果哪天不只一台機器跑 `bin/dev-flow-worker`（例如 Mac 加上 P14），現有架構哪些部分撐得住、哪些會壞、要補什麼。

同時它也是名詞說明。分散式協調的術語在文獻裡有固定講法，這裡每個名詞都配上 dev-flow 裡的實際對應，避免只記得詞而講不出它解決什麼問題。

## 先講結論

現有架構**已經有搶佔，但沒有租約**。單機時這個缺口的後果是 Issue 偶爾卡住，人工兩分鐘可修；多機器時同一個缺口會變成沒有人能接手，而且無法從外部判斷擁有者是否還活著。

真要跑兩台，**第一選擇是按 repo 分區**，零程式碼、零協調。只有在 worker 數量多到需要動態負載平衡時，才值得付 lease 加 fencing 的代價。

## 名詞

### 單寫者（single-writer）

**白話**：同一份資源，同一時間只允許一個人寫。

**為什麼需要**：兩個人同時改同一個東西，結果取決於誰先到，這叫競態（race condition）。最簡單的解法不是把並行寫入做對，而是根本不要有並行寫入。

**dev-flow 對應**：`<workspaceRoot>/.orchestrator/queue-poll.lock`，用 `mkdir` 的原子性當鎖。`mkdir` 在目錄已存在時會失敗，這個「建立或失敗」的性質就是鎖。它保護的是**這一台機器的工作區**，不是全域佇列，所以多機器時每台仍各自需要一把。

### 競爭消費者（competing consumers）

**白話**：多個 worker 盯著同一個佇列搶工作。

**為什麼需要**：這是最常見的水平擴展方式。難處不在於「怎麼分工」，而在於「怎麼保證同一件事不會被兩個人同時做」。

**dev-flow 對應**：目前只有一個消費者。選取順序刻意寫成決定性的（跨 repo 依 `createdAt` 遞增，時間相同才用 repository 名稱與 Issue 編號打破平手，且以 code unit 比較而非 `localeCompare`），就是為了讓不同機器對同一個佇列排出完全一樣的順序。兩個 worker 會同時看上隊首那一個，接著由下面的 CAS 決勝。

### Compare-and-set（CAS，也叫 compare-and-swap）

**白話**：「只有當它現在還是我以為的樣子，才幫我改。」條件判斷和寫入是同一個不可分割的動作。

**為什麼需要**：如果先讀再寫（check-then-act），兩步之間可能被別人插隊。CAS 把兩步合成一步，由被寫的那一方（資料庫、檔案系統、GitHub）保證原子性。

**dev-flow 對應**：搶佔用的是 `POST /repos/{owner}/{repo}/git/refs` 建立 `refs/dev-flow-claims/issue-<n>-attempt-<k>`。ref 已存在時 GitHub 直接回 `Reference already exists` 而失敗，只有一個 worker 會成功。關鍵在於**仲裁者是 GitHub 伺服器**，不是任何一台機器，所以不需要共享檔案系統，兩台機器也不必看得到彼此。

同類機制：Redis 的 `SETNX`、SQL 的 `INSERT ... ON CONFLICT DO NOTHING`、檔案系統的 `O_EXCL`。

為什麼不用 label 當鎖：改 label 是「讀了再寫」，兩個 worker 可以同時讀到 `dev-flow-ready` 然後都改成 `dev-flow-running`，都認為自己贏了。label 是狀態顯示，不是併發控制。

### 租約（lease）與可見性逾時（visibility timeout）

**白話**：搶到工作時不是永久擁有，而是拿到一段有期限的使用權。時間到了沒續約，這份工作就自動回到佇列。

**為什麼需要**：擁有者可能死掉。如果所有權沒有期限，一次當機就讓那份工作永遠沒人能碰。租約把「需要判斷對方死活」換成「看時鐘」。

**dev-flow 對應**：**目前沒有**。claim ref 一旦建立就永久保留（保留是刻意的，它是 attempt 唯一性的依據）。這正是 2026-08-10 的事故：worker 被 SIGTERM 之後 Issue 永久停在 `dev-flow-running`，選取階段跳過它，而 resume 需要一則帶 attempt marker 的報告才算得出編號，兩條路都不通，只能人工刪 ref、移除 worktree 與 branch、改回 label。

SQS 的同一個概念叫 visibility timeout：訊息被取走後暫時隱形，處理完就刪除，沒刪除且逾時就重新可見。

### 心跳（heartbeat）與續約（renewal）

**白話**：執行中的 worker 定期回報「我還在」，藉此延長租約。

**為什麼需要**：租約期限要同時滿足兩個矛盾的需求。設短了，正常但耗時的工作會被誤判成死亡；設長了，真的死掉時要等很久才能回收。心跳讓你把期限設短（例如兩分鐘），由續約來支撐長工作。

**dev-flow 對應**：目前沒有。要做的話，執行期間定期更新 claim ref 指向的物件，並用「指定舊值」的方式更新（`git update-ref <ref> <new> <old>` 就是一次 CAS），這樣殭屍 worker 的續約會因為舊值對不上而失敗。

### 故障偵測器（failure detector）與「死了 vs 很慢」

**白話**：從外部判斷另一個節點是不是掛了。**這件事在分散式系統裡辦不到。**

**為什麼重要**：你觀察到的只有「它沒有回應」。沒有回應可能是它當機了，也可能是它正忙、網路塞住、或封包在路上。這兩者從外部完全無法區分（理論上的結果，不是工程沒做好）。所以任何「先判定對方死亡、再搶走它的工作」的設計，本質上都在賭。

**dev-flow 對應**：Issue #29 就是撞在這裡。它想用 process ID 判斷擁有者死活，但：

- PID 只能查同一台機器，跨主機無解。
- PID 會被作業系統回收再利用，「這個 PID 存在」不等於「我的 worker 還活著」。
- GitHub label 與本機 ledger 是兩個獨立儲存、分兩次寫入，中間必有窗口。死在窗口裡就沒有記錄可查，只能猜，猜錯會把 `dev-flow-resume` 誤降成 `dev-flow-ready`，弄丟授權。

跑滿 4 cycles、15 條 findings（3 條 High）之後放棄，改成 Issue #31 的純時間門檻**只標記不回收**：標記猜錯的代價只是一則誤報留言，不會有人被搶走工作。

正確的思路是把問題換掉：不要問「它還活著嗎」（問不出來），改問「租約到期了沒」（看時鐘就知道）。

### 殭屍（zombie）與腦裂（split brain）

**白話**：被認定死亡、實際還活著的節點。腦裂指兩個節點同時認為自己是擁有者。

**為什麼需要在意**：租約到期只代表「你沒有續約」，不代表「你停止運作了」。舊 worker 可能只是暫停或網路斷線，恢復後繼續做它以為還屬於自己的工作。

**dev-flow 對應**：如果加上租約回收而沒有下一項，舊 worker 會 push 到同一個 branch 名並開 PR，跟新 worker 互相覆蓋，而且錢付兩次。

### Fencing token

**白話**：每次所有權轉移，發一個更大的號碼；**真正被寫入的那一方**要檢查號碼，小的一律拒絕。

**為什麼需要**：這是唯一能擋住殭屍的機制。鎖本身擋不住，因為殭屍手上還握著一把它以為有效的鎖。防線必須設在資源端，不是鎖端。（Martin Kleppmann 那篇談分散式鎖的文章就是在講這件事。）

**dev-flow 對應**：attempt 編號已經有 token 的形狀，claim ref 也是 per-attempt 的。缺的是**寫入端的驗證**：在 commit、push branch、建立 Draft PR 之前，再確認一次「我仍持有當前 attempt 的 claim」，不成立就中止。目前發布流程不做這個檢查。

### At-least-once、at-most-once、exactly-once

**白話**：一件工作被執行的次數保證。

- **at-most-once**：最多一次，可能一次都沒做（失敗就放棄）。
- **at-least-once**：至少一次，可能重複（失敗就重試）。
- **exactly-once**：剛好一次。端到端而言做不到，實務上談的是 **effectively-once**：允許重複執行，但用去重讓**副作用**只發生一次。

**dev-flow 對應**：搶佔加上「不自動回收」，目前偏向 at-most-once，代價就是卡住要人救。一旦加入租約回收就變成 at-least-once，這時副作用的去重就變成必須，否則會出現重複的 branch 與重複的 PR。

### 冪等（idempotency）

**白話**：同一個操作做一次和做十次，結果一樣。

**為什麼需要**：at-least-once 的世界裡重複執行是常態，把副作用設計成冪等，重複就不痛。

**dev-flow 對應**：branch 名 `codex/issue-<n>-<slug>` 天然是一個去重鍵。建立 Draft PR 之前先查該 branch 是否已有 PR，就能避免重複開。留言則需要像 needs-human 報告那樣埋一個 marker 才能判斷是否已經貼過（Issue #31 的標記留言就是用這個手法做冪等）。

### 分區（partitioning / sharding）

**白話**：把佇列切成幾份，每份固定由一個 worker 負責。

**為什麼需要**：這是**避免**分散式協調而不是解決它。每個分區退回單寫者，租約、fencing、去重通通不需要。

**dev-flow 對應**：`DEV_FLOW_ALLOWED_REPOS` 現成就能做到。Mac 只吃 `skai-in-ai/dev-flow`，P14 只吃 `content-studio`，兩者永遠不會爭同一個 Issue。代價是負載不均，且某台掛掉時它那一區停擺（但那本來就需要人介入）。

## 現況對照表

| 機制 | 有沒有 | 位置 |
|:---|:---|:---|
| 決定性選取順序 | 有 | `orderQueue()` |
| 單機單寫者鎖 | 有 | `acquirePollLock()`，`mkdir` 原子性 |
| 跨機器搶佔（CAS） | 有 | `claim()`，GitHub ref 建立 |
| 租約到期 | **沒有** | claim ref 永久保留 |
| 心跳續約 | **沒有** | |
| Fencing（寫入端驗證） | **沒有** | 發布流程不重驗 claim |
| 副作用去重 | 部分 | branch 名可當去重鍵，但建 PR 前不查 |
| 卡住的可見性 | 進行中 | Issue #31，逾時只標記不回收 |

單機單寫者鎖的細節：同 host 且 owner PID 存活就保持有效，不論經過多久；同 host 但 PID 已死可立即回收；foreign host、無法驗證或 metadata 損壞，才退回 30 分鐘的時間門檻。注意這裡對 PID 的用法是安全的，因為它保護的是本機工作區，判斷對象就在同一台機器上。#29 之所以不成立，是它想把同一招用在**跨機器**的所有權判斷上。

## 加第二個 worker 會壞在哪

**場景一：擁有者死亡，沒有人能接手。** worker A 搶到 Issue、建了 attempt 1 的 claim ref，然後機器休眠。ref 還在，label 還是 `running`。worker B 看不到這個 Issue（選取排除 `running`），就算看到也建不了同一個 ref。這個 Issue 需要人工介入才能繼續。

**場景二：claim 與 label 之間的窗口。** 目前流程是先建 ref，再把 label 從 ready 換成 running。死在中間的話，GitHub 上 label 說「待執行」但 ref 說「已被搶走」。worker B 看到 ready 去搶，CAS 失敗，接著的行為沒有明確定義。單機幾乎遇不到，多機器會放大。

**場景三：假設補上了租約回收，但沒有 fencing。** B 接手後 A 醒過來，兩者 push 到同一個 branch 名、都嘗試開 PR。偵測正確也擋不住這件事，因為問題不在偵測，在寫入端沒有防線。

## 真要做的話

1. **把租約放進 claim ref。** ref 指向的物件帶到期時間，狀態只存在 GitHub 一處，本機 ledger 退回純稽核用途。這樣「單一權威儲存」成立，不會再有兩個儲存分兩次寫的窗口。
2. **心跳用指定舊值的 ref 更新。** 那是一次真正的 CAS，殭屍的續約會因為舊值不符而失敗。
3. **發布前重驗 claim。** commit、push、建 PR 之前確認仍持有當前 attempt 的 claim，不成立就中止。這是 fencing 的落點。
4. **建 PR 前先查該 branch 是否已有 PR。** 讓發布這個副作用冪等。

順序不能顛倒：只做 1 和 2 而沒有 3，等於把 at-most-once 換成沒有防護的 at-least-once，比現在更危險。

## 為什麼現在不做

- 目前只有一台機器一個 worker，租約與 fencing 解決的是「多個 worker 競爭」，那是還不存在的問題。
- 卡住的 Issue **不阻塞佇列**：選取直接跳過它，其他 Issue 照常處理，影響範圍就是那一個。
- 手動救援是三個指令：刪 claim ref、移除 worktree 與 branch、把 label 改回授權狀態。
- 要動的程式碼在 claim 這條路上，是整個系統最危險的地方。為了罕見、不阻塞、兩分鐘能修的問題去改它，划不來。

Issue #31 的逾時標記只補「看得見」這一項，而且刻意不碰 claim 路徑。

## 什麼時候該重新評估

- 真的讓第二台機器（例如 P14）也跑 worker，而且不採用分區。
- 任務量成長到需要動態負載平衡，分區的不均開始造成明顯等待。
- 出現「同一份工作被跑兩次」的實際案例，而不只是理論上的可能。

前兩項發生時，先試分區。分區撐不住了，再照上一節的四個步驟做，並且先寫設計文件，不要直接開成 dev-flow 的 Issue：這是架構改動，不是一份 spec 描述得完的增量。
